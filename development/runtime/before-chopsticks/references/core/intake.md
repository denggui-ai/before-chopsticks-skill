# 照片入口与路由

用户发来一张或几张自己拍的菜品照片（可附一句话或不附）时读本文件。目标：第一条回复就让用户感到"看懂了我的菜、比我会拍、不会乱动我在乎的东西"；用户只需回一句就进入正确路线；每次会用掉的生成次数都在用户点头前说清。设计默认值查[styling.md](styling.md)；摄影方法查[photography.md](photography.md)；版本与执行查[state.md](state.md)、[codex.md](../hosts/codex.md)。

## 什么时候生成

只有三类话会触发生成：

1. 首句就明确要一张图（"帮我重拍一张""把这张修好看""做一张白底"）。
2. 用户明确说开始（"开始做""行，做吧""就按你说的"及同义说法）。
3. 认可先做的那一张并说继续。

其余（补充要求、提意见、选方向、问问题）只更新要求并复述，等待开始。一句里同时有要求和开始（"铜锣烧不要，开始吧"）＝更新后直接开始。自由回复先用一句话复述理解再归类，拿不准不生成。

首句已有明确意图时：

- **只调色**（"调亮一点""暖一点""裁一下"）：0 次，只用 `state.py` 的 `local_edit`，**不调用原生图像工具**；结果后附一句"想换光或挪东西可以重拍，用 1 次"。任何原生图像调用都必须按 `prepare` → `preview` → `dispatch` 进行，`dispatch` 返回 `dispatching` 后才调用，不得直接调用。
- **明确要一张图**：视为授权 1 次，先完成下文分组、质量判断和三层拆解并落实保住项，直接执行；结果回复写"保住了…；改了…；用了 1 次"。只有存在待确认事项时才退回短确认：认不出菜、多图里底图不明、画面有人且用户还没表态是否保留（已表态则沿用，不重复问）。直接执行时不新增会改变人数、份量或身份表达的道具，只改光、角度、取景、色彩、食物状态和中性环境。
- **明确要一套**（"做一套""做成制作过程"）：短确认。

## 多图分组

先按关系分组，混合时分别处理：

| 关系 | 默认推荐 | 执行 |
|---|---|---|
| 同一道菜的不同阶段 | 升级成一套，先做一张看看 | `narrative_series` |
| 几道不相关的菜 | 各自一张 | `independent_items`，一次说明共 N 次，开始后逐张出 |
| 同一时刻多角度 | 挑一张作底图并说为什么 | 单图 |
| 其中一张像参考（别人的作品、风格明显不同、用户说"这种感觉"） | 按下文"参考图" | 参考不计入出图张数 |
| 看不准 | 首答里只问一句，合并所有不确定："这几张是同一次做的吗？第 N 张是想参考的感觉吗？" | 不确定时按各自一张，光线统一作为建议 |

**做一套先做一张**：先做信息最丰富、最能体现改进的一张，首答写"先做第 N 张，用 1 次；满意再用同样的光和台面做其余 M 张，再用 M 次"。这一张的结果回复末尾固定写："满意回『继续』，再用 M 次做其余 M 张；想改哪里直接说。"对它提意见＝只修这一张，复述写"先修这一张，其余会跟着它做"，每次修正单独说明并等点头，不出其余。张数多（如超过 5 张）同样先做一张，再按代表性推荐张数。

作品项目建在当前工作目录下（如 `works/<菜名>`），不建在临时目录，以便之后继续修改和找回。

执行顺序（建组时成员即固定，没有后补项接口）：每张原图 `create_work`＋`import_image` → `create_group`（全部 work_ids）→ 先做的那一张 `prepare` 带 `group_id/item_id` → 成功后 `set_series_anchor`（borrowed_roles 如 lighting、color、material）→ 为每个后续项建立承担锚点借鉴的 Reference → `set_item_anchor` → 各项 `prepare.references` 显式提交该 Reference。编辑输入总数 ≤3（含主底图）。

## 入口质量

| 原图 | 处理 |
|---|---|
| 能认菜、细节够 | 正常 |
| 能认但模糊或太暗 | 点名哪些细节会"按常见样子补" |
| 认不出 | 问"这是 XX 吗？"；不是→请用户说菜名；用户也说不清→推荐补拍要点或按菜名重画（不参考原图，用 1 次），二选一并给推荐 |
| 已经很好 | 直说好在哪；推荐只调色（0 次），或给 1–2 个换感觉的方向；不为改而改 |
| 不是食物 | 说明能做什么，不硬套 |

首答第一行末尾固定写"（看错了直接告诉我）"。

## 三层拆解与物件

| 层 | 内容 | 谁说了算 | 默认 |
|---|---|---|---|
| 身份 | 菜、器皿、搭配食物、可能有含义的物件、地点线索、画面中的人 | 用户 | 保住；用户可放掉 |
| 状态 | 摆放整齐度、光泽、新鲜度、热气、与时刻一致的过程痕迹 | 我们 | 在"还是这道菜"内适度改得更诱人并说出来；处理不等于拉满，不做塑料感或白雾式热气 |
| 拍法 | 光、角度、取景、色彩 | 我们 | 全权重做 |

| 物件 | 例子 | 处理 |
|---|---|---|
| 食物、器皿 | 包子、蓝碗、蒸纸 | 保住，尽量保持外观特征 |
| 可能有含义的物件 | 外文包装盒、擀面杖、碎花纸、带店名的袋子 | 留着，放到边上不抢主角，字仍可辨；首答点名 |
| 过程痕迹 | 擀面撒落的面粉、开吃的碎屑 | 与时刻一致→保留；与时刻无关→可收拾但首答点名 |
| 明显无含义的意外入镜 | 无字无品牌的半截塑料袋 | 收拾，首答点名，用户可否决 |

- 拿不准有没有含义时，一律按"可能有含义"处理。
- 画面里有人脸、孩子：属于身份，默认原样保留并提醒"重拍时人脸可能被改变"；用户可要求裁掉或只留手。
- 用户锁定但不好看的地点或背景，保留含义、不照抄样子；菜与器皿不适用这一条。
- 两道菜：用户没提都保留；主次由我们定并说明。
- 不对身份处境下结论（外文包装不等于身在国外）。

## 第一条回复

**完整首答**（无意图或弱意图，如只发图、"这是我做的菜"）：第一轮不出图，只给一条推荐，不列抽象菜单，不问用途。单图约 200 字、6–8 行、不用表格；多图每张一行，约 300 字。每条改动附约 15 字以内的理由。

```
<看到的：点名菜和器物，先说好的>（看错了直接告诉我）
保住：<菜、器皿、搭配>；<有含义物件>我留着，放到边上。
我会改：<改成什么＋半句理由>；<…>；按<画面场景>搭配：<最多 3 件新增道具及理由>
开始做会用 1 次生成。<最高风险一句>。之后每次修改都会先问你。
可以回：「开始做」/「<真实元素>不要」/「做一套」；只调色不挪东西也行；要白底、换背景或照某张图的感觉，直接说。
```

多图时第 2–3 行改为每张一行（"1 包：保住…；改…"），并写先做哪一张与总次数；关系看不准时加问一句。

**短确认**（明确要一套，或明确要一张但有待确认事项）：≤4 行，写保住、改、用几次、回"开始做"。因待确认事项退回时，必须把那个具体问题写进去（"这是酸汤鱼吗？""用第 2 张当底图？""画面里的人留着吗？"）。用户只回"开始做"而问题未答时，先按推荐答案复述一句再执行；推荐答案也拿不准则不执行，重问。

**只改要求后的复述**：写更新后的保住与改动、次数，末尾固定"回『开始做』我就做"。一句里同时有要求和开始时不加这句，直接做。

**开始生成前**：一句"开始做了，出来给你看"，不预估时长。

**语气与用词**：只说"我会改成什么"，不说"原来哪里不好"；不说乱、脏、垃圾。不在回复里引用规则文件或说"规则要求"。不说免费或付费，只说次数：实际用了生成就写明"用了 N 次生成"。回复中不出现内部术语：

| 内部 | 对用户说 |
|---|---|
| 身份层、状态层、拍法层 | 不说层名 |
| 让位 | 留着，放到边上 |
| 样张、锚点 | 先做一张看看 |
| 额度 | N 次生成 |
| 本地轻修 | 只调色 |
| 生成式编辑、重拍 | 重拍（用 1 次） |
| `画面来源` 值 | 你的照片 / 我设计的画面 |

## 路由

| 用户回复 | 执行 | 授权 | 必说的实话 |
|---|---|---|---|
| 首句明确要一张 / 开始做（单图） | `create_work`＋`import_image` → `generative_edit`，父版为导入原图 | `authorize(requested_count=1)`，evidence 指向该消息 | 细节可能细微变化 |
| 开始做（一套） | 见"多图分组"执行顺序 | `authorize(1)` 只给先做的那一张 | 先 1 次，其余等你认可 |
| 认可并继续 | 锚点绑定后逐项 prepare | 新 `authorize(M)`，evidence 指向"继续"消息 | 共 M 次 |
| 点头修正某张 | 以该版为父版 `generative_edit` | 新 `authorize(1)`；不用 `extend_retry_budget`（它只扩重试额） | 用 1 次，报累计 |
| 开始做（各自一张） | `independent_items`，每项父版为各自导入原图 | `authorize(N)` | 共 N 次 |
| 只改要求 | 复述，等开始；开始时随 `prepare.changes` 提交，来源 `user_explicit` | 无 | — |
| 只调色 | `create_work`＋`import_image` → `local_edit` | 无（0 次） | 不能挪东西、不能改光；首答承诺的收拾或放边上在此路线不兑现，要说并提供重拍 |
| 去背景 / 白底 / 去掉某物 | 原生语义编辑；透明底用 `transparent_background` | `authorize(1)`：首句已明确则直接用，否则等开始 | 用 1 次；主体可能被重画 |
| 补全成一个故事 | 策划卡片 | 无 | 卡片写总次数 |
| 给几个方向 | 2–3 个具体方向，只读，按[interaction.md](interaction.md)探索规则 | 无 | 不出图 |
| 怎么拍 / 拍得怎样 | 点评或实拍指导，只读 | 无 | 不出图 |
| 认错菜、关系答复 | 回到分析，重出首答或短确认 | 无 | — |
| 要加字（"加一句…""放个 logo"） | 不出图；说明"加字功能还在做，目前不会把字画进图里"，可给 2–3 条文案建议 | 无 | 字画进生成图会变形 |
| 原生图像工具不可用 | 说明缺口，不用旧 CLI 或其他渠道补位 | 无 | — |

"回第一版继续""看第一版"沿用[interaction.md](interaction.md)的选版规则。

## 需求记录

- **单图**的保住、放掉、改动写进 `prepare.changes`，来源如实：用户说的 `user_explicit`；用户没说、但照片里真实可见的身份元素用 `user_implied_edit_preservation`——只用于照片里真实可见的默认保留项，不用于推测的偏好或我们新增的设计；我们的改动 `ai_design`。**不要用 `default` 记身份保留**：`default` 低于 `ai_design`，会被风格展开覆盖。
- 设计展开不得生成与身份保留冲突的条件。引擎只裁决同键冲突，不同键的语义冲突须在准备时按[styling.md](styling.md)的统一优先级自查。
- **一套图**：`prepare.changes` 只作用于单个 Request，后续项不继承。用户对整套说"开始做"时，首答或卡片中已确认的整组条件（统一光与台面、整组保住项）用 `add_requirements` 记为 group 作用域，`message_id` 用该消息的 ID；单张专属条件仍逐项放 `prepare.changes`。用户明确说"以后都"才用 project 作用域。
- **`画面来源`**：每张图的依据用专用需求键 `画面来源` 记录，值 `用户照片` 或 `设计画面`，来源 `ai_design`，只由本 Skill 写入，不得用其他来源写这个键，同一轮不得写两个值。每个 Work 或组项首次 prepare 时写入；之后每次 prepare 前检查有效要求里该键存在且值正确，缺失或被冲掉才补写——这是"已有要求不重复添加"的明确例外。换 Work 时该键不随借用条件继承，须重新写。交付标签读目标 Version 的有效要求，不从父版或参考推导。

## 套图：升级、补全与策划卡片

两种深度：**升级**（只做用户拍的几张）为默认；**补全**（补出缺的节点）作为一句可选项提出，并说明补出的是"我设计的画面"。默认故事骨架"来源 → 备料 → 烹饪 → 成品 → 开吃"，按菜增删（虾：海面 → 捕捞 → 活虾 → 下锅 → 上桌）。

卡片格式（表格只在卡片里用）：

```
故事线：<一句>，共 N 张（先做 1 张看看，满意再做其余；共 N 次生成）
| # | 画面 | 来自 | 为什么这样拍 |
人物：<如"渔民只拍手、不露脸"> ｜ 也可以露脸，或你来定
可替换：<一个开关，如"第1–2张可换成海鲜市场">
需要知道：我设计的画面不是实拍；几张之间不保证一模一样
可以回：开始做 / 改第2张… / 删第3张 / 加一张… / 换海鲜市场
```

- 只给一条故事线和一个可替换开关；用户明确要几个方向时走探索。
- "画面"列写清每张的道具，制作中与成品分开写（制作中：原料、工具、半成品、过程痕迹；成品：餐具、配搭），道具规则见[styling.md](styling.md)"画面场景与道具"。
- 人物露脸未定时，在"人物"行同时给默认与选择，不把不露脸设为全局默认；已明确则遵循。
- 品种或来源拿不准（海捕、养殖、市场）时作为可替换项，不硬定；"我设计的画面"不写成事实陈述（不写"产自""捕自"）。
- 卡片上的改、删、加、换只更新卡片；"开始做"才进入先做一张。
- 计划内的"我设计的画面"项：若用新生成（不能带参考），在提示词里用文字写清已定那一张的光、色、台面；若用编辑带参考，先建对应 Work、导入底图为其 Version 并指定父版，再加用户照片或锚点 Reference，总输入 ≤3。
- 交付时每张图下标"你的照片"或"我设计的画面"。

次数：N 为初始计划。任何项的修正另说明、另点头、另计；失败或 `unknown` 走现有恢复规则（`unknown` 不释放、不自动重发），续做前重新说明剩余次数。

## 出图后

- 原图与新图依次展示并对应标签；宿主不支持并排时按顺序发，不另做拼图，除非用户要。
- 逐项核对默认保住的项和用户新锁定的项，一行一项："碗：颜色对，纹理略细；青菜：在；铜锣烧：在，但变成三块。要修哪个？"肉块形状、青菜样子、釉面纹理、筷子材质易漂，优先核对。
- 修正：说明修什么、用 1 次、累计已用几次，等点头。用户不修→结束或换路线（只调色原图）。
- 同一问题两次未达成即停：先按[photography.md](photography.md)的 P-CHECK 核对请求与输入有无漏写或误锁，说"这次尝试没做到"，不说"工具极限"；给替代（只调色原图、接受当前、从较好的一版另开分支）。
- 修正总次数没有自动上限，但每次都需点头。
- 用户没要透明底时，检查新图有无透明像素；有明显透明区域（如边角、背景被挖空）要告诉用户，并提供修正（用 1 次）或改用只调色原图。带 alpha 通道的原图（即使全不透明）更容易出现这种情况。

## 参考图

用户发自己的菜＋一张参考（"我要这种感觉"）。按话语和顺序区分"我的菜"与参考；分不清时首答里问一句。

| 默认借 | 默认不借 |
|---|---|
| 光的方向与软硬、影调明暗、色调冷暖、机位与构图方式、留白、台面与背景材质、道具风格 | 参考里的菜、具体器皿、人物、品牌与文字内容 |

- 用户的器皿与参考的器皿冲突时，默认保用户的；用户明确要换则照换。
- 借属性，不照搬参考的摆位与构图细节；不复刻可识别构图，不带入商标与文字。不核查参考图的授权。
- 首答写清"从参考借：…；不借：…"，点名 2–3 个最强的感觉因素，让用户纠正。
- 登记：参考图 `import_asset`（只登记素材，不建作品版）→ `add_reference(asset_id, roles, scope)`，`roles` 为对象列表（每项含 `role/borrow/exclude/strength/source`），exclude 写清菜品、器皿与品牌文字 → `prepare.references` 显式提交其 Reference ID。
- **借来的感觉只写在 Reference 的 roles 里。** 若还要把它写成需求，来源用 `ai_design`，不用 `user_reference`：`user_reference` 高于 `user_implied_edit_preservation`，同键时会替换照片里用户自己的东西。
- 单图：用户照片为主底图，参考为辅助 Reference，总输入 ≤3。一套：参考的感觉作为整组共享要求，先做一张；认可后后续项输入为"底图＋锚点＋参考"恰好 3 张，不能再加。新生成不能带参考：把参考拆成文字写进提示词。
- 参考里的文字版式只记版式感觉（字体气质、位置、大小比例），不借文字内容和 logo。
- 实话：属性不保证干净分离，可能串入参考里的菜或盘子；出图后逐项核对"借到了什么、串进了什么"。

## 交付边界

- 本地调色裁切保留原图已有的 ICC 配置，不转换到 sRGB，也不补配置文件；只支持单帧 8-bit RGB/RGBA。RAW、高位深和印刷交付不支持，用户提到时先说明；需要 sRGB 转换属于另外的功能，当前没有。
- 平台常用比例与一次裁出多个比例见[interaction.md](interaction.md)的"比例预设"。
