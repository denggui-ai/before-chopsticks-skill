# 照片入口与路由

每条消息都从这里接入，包括无图、只发图、创作后修改和中途换菜。先认素材职责，再看原图条件、有参考则定借法，再判断创作、修改、只给建议或加字；交付后回到入口。设计判断查[styling.md](styling.md)，摄影方法查[photography.md](photography.md)，版本与执行查[state.md](state.md)、[codex.md](../hosts/codex.md)。

## 认图与提问

依据用户的话和前后文，将图认作自己的菜、外部参考、之前作品或现场照片，不依上传顺序认角色。能确定就做；低风险歧义采用默认并简述。只有误判会造成较大代价时才问，一轮最多一个问题，附推荐及简短理由；“嗯／好”等短答表示同意当前推荐。没有可合理猜定的菜名时，请用户说明菜名，推荐补名称或清楚照片，不硬猜。不得询问发布用途或平台，不做平台规则、发布或商用安全审核。

常见情况按以下顺序判断，前一项适用就不重新从后面开场：

1. 已有作品，前文正在等素材：将新图接到所等镜头或修改，不重问已知菜名与意图。
2. 已有作品，又发新图但不说话：询问换菜还是用作参考，附依据图像与当前作品的推荐，不自行切换。
3. 无作品、只发一张图：能认作菜就点评可见优点并给一句具体推荐，不生图、不列方案菜单；照片已很好就直接说好在哪，不为改而改。疑似外部作品则问是自己的菜还是参考并附推荐；认不出菜则问菜名，不硬猜。
4. 多张图不说话：判断并说清是同菜不同阶段、同菜多角度、多道菜同桌或各自独立，还是菜与参考；同桌关系须有环境、餐具等图像依据，看不出才问一个关键关系问题并附推荐。没有创作指令时不由分组自动开拍。
5. 只有参考、没有自己的菜：先认角色；确认是参考后，问创作一道类似的菜还是等用户发自己的菜来套用感觉，附推荐。角色明确时不再重问。
6. 无图无话：简述可创作单图／套图／方向、修改照片、点评与实拍建议、加字四件事，其中加字暂不支持；问拍什么菜，推荐先给菜名或菜图。

## 什么时候生成

先判断本轮做什么，再判断能否执行。只发图、补充信息、选方向、问问题不自动变成生成指令；“先说方案／不要生成”只做对应方案，不创建生成 Attempt。只调色、裁切走本地 `local_edit`，0 次生成；点评、方向与实拍建议不生成。创作方案、修改表达与授权统一见“创作：策划与方案”和“路由”。一句里兼有更新要求与开工指令时，先更新再按有效授权执行，不另设确认口令。

## 多图分组

先按关系分组，混合时分别处理：

| 关系 | 默认推荐 | 执行 |
|---|---|---|
| 同一道菜的不同阶段 | 先识别阶段关系，按用户意图决定创作或修图 | 按“创作：策划与方案”或修改边界处理 |
| 几道不相关的菜 | 各自一张 | `independent_items`，一次说明共 N 次，开始后逐张出 |
| 同一时刻多角度 | 挑一张作底图并说为什么 | 单图 |
| 其中一张像参考（别人的作品、风格明显不同、用户说"这种感觉"） | 按下文"参考图" | 参考不计入出图张数 |
| 看不准 | 按“认图与提问”只问最影响方案的一个关系问题并附推荐 | 先不确定分组，不以各自一张擅自兜底 |

整套开工与续作按“授权与张数”；发现身份、锁定项或故事目标未达成时暂停受影响项并说明。

作品项目建在当前工作目录下（如 `works/<菜名>`），不建在临时目录，以便之后继续修改和找回。

执行顺序（建组时成员固定，没有后补项接口）：

1. 依完整脚本确定全部镜头，再为计划内各项 `create_work`，编辑项 `import_image`，用全部 `work_ids` 建 `create_group`；保存组级设计和限定范围的连续条件。按各镜头选路径，不为凑统一操作全部绑定原图。
2. 逐项 `prepare` 带 `group_id/item_id`、本张任务与适用参考。第一张用完整文字设计，不额外出场景图；不要求先生成样张或等用户认可才完成已批整套。
3. 同场景与转场分别写适用的空间、人物、服装、光色条件，排除不适用的旧摆位、姿势与阶段。同一场景的套图，第一张成功并自查通过后，后续同场景、机位高度与第一张相同的镜头从这一张出发：`import_image` 导入本项作品作父版（只给已在组内的本项作品加版本，不改组成员），按下文“按镜头选执行路径”第 2 条用 `explicit_scope`，`borrow` 写菜身份、场景器物、人物服装与光色，`exclude` 写第一张的构图、机位、动作与食物阶段；只从第一张出发，不拿后续成图串链；`画面来源` 沿用本套原值，不因导入而标成用户照片。导入版只作父版，交付的是本次编辑出的新版；第一张自查不过就不导入，先按“出图后”处理，第一张换版后未提交的后续项改从新版出发。机位高度与第一张不同的镜头（如斜俯换顶拍或平视）不导入，因编辑会把第一张的取景带过来；改用文字新生成，把桌面、器物、人物服装、光向光色与菜的样子按第一张写具体。转场镜头同样不导入，用文字设计。单张重拍按“同套连续性参考”。
4. 新生成不带原片、锚点或父版（同场景且机位高度与第一张相同的镜头按第 3 条走编辑路径）；编辑输入总数最多三张含主底图。建组后需增删成员时另建组并说明剩余次数，不改写旧组或已有调用事实。

## 原图条件与提醒

条件分档只决定提醒与推荐，不自动触发修改或切换工具。

| 条件 | 何时说、怎么做 |
|---|---|
| 小问题：稍暗、轻微偏色 | 不单独提醒，按本轮目标处理 |
| 中等：有点糊、局部过曝、菜或盘边被切、光硬 | 照常处理，不要求先重拍；记下条件，交付时用一句话说明能做到的范围与照片条件，并给一条下次补拍建议 |
| 大问题：局部修不好，须改构图、用光或菜态 | 生图前先说能做到什么及限制，推荐按照片重拍或补清楚素材；需要放宽保留条件时才问，不擅自丢锁定项 |

说照片条件，不评价拍摄者；先说能做到什么，补拍建议面向下次更出彩，合为一句简短说明。同样适用于参考与原图差距大、点评时的补拍建议。已提示事项记入作品记录，避免反复责备或重复阻塞。

身份细节确实不足时，按已知菜名文字新生成可作为降级建议：须先说明哪些细节只能按常见样子补、可能不像原来的菜，标作设计画面；菜名未知不生成。文字重建不能满足精确保留器皿、人物或其他锁定项时，请补清晰素材或放宽条件；原生成授权不等于同意丢锁定项。只调色、裁切仍为本地处理，不因原图模糊自动转生成。

## 三层拆解与物件

下表用于单图及多张**修图模式**：以指定照片为依据，只改本轮目标及必要联动、保留未改项，不补故事，不强制改光、机位或台面。需要生成式编辑时说明实际张数与次数；仅调色裁切仍走本地处理。创作的默认保留范围见[styling.md](styling.md)“任务边界与路线”。

| 层 | 内容 | 谁说了算 | 默认 |
|---|---|---|---|
| 身份 | 修图与创作的身份范围见[styling.md](styling.md)“任务边界与路线” | 用户 | 保留项可由用户明确放开 |
| 状态 | 摆放整齐度、光泽、新鲜度、热气、与时刻一致的过程痕迹 | 我们 | 在"还是这道菜"内适度改得更诱人并说出来；处理不等于拉满，不做塑料感或白雾式热气 |
| 拍法 | 光、机位、取景、色彩、台面、背景 | 我们 | 只调整本轮需要改变的项目；用户锁定条件优先 |

| 物件 | 例子 | 处理 |
|---|---|---|
| 食物、器皿 | 包子、蓝碗、蒸纸 | 保住，尽量保持外观特征 |
| 可能有含义的物件 | 外文包装盒、擀面杖、碎花纸、带店名的袋子 | 留着，放到边上不抢主角，字仍可辨；首答点名 |
| 过程痕迹 | 擀面撒落的面粉、开吃的碎屑 | 与时刻一致→保留；与时刻无关→可收拾但首答点名 |
| 明显无含义的意外入镜 | 无字无品牌的半截塑料袋 | 收拾，首答点名，用户可否决 |

- 拿不准有没有含义时，一律按"可能有含义"处理。
- 画面里有人脸、孩子：属于身份，默认原样保留并提醒"重拍时人脸可能被改变"；用户可要求裁掉或只留手。
- 用户锁定但不好看的地点或背景，保留含义、不照抄样子；菜与器皿不适用这一条。
- 两道菜：用户没提都保留；主次由我们定并说明。
- 不对身份处境下结论（外文包装不等于身在国外）。
- 器皿或有含义物件与用户点名的风格、影调冲突时，首答点名并给出口，如“花盘会拖住极简感，默认留着，想换说一声”；用户点名换时记 `user_explicit`。不能仅因风格冲突擅自删掉默认保留物件。
- 承诺改变哪项拍法，就将那项具体设计写入请求；只调色、裁切与局部修改不机械重设全部拍法。

## 第一条回复

按本轮意图自然回复：无意图先点评与一句推荐，不生图；明确创作按“方案表达”给相应方案及收尾；修改只说改什么、保留什么。首句、措辞和排版自然，不列回复菜单。授权判断见“授权与张数”。

**开始生成前**：简述实际计划与生成次数，不预估时长，不用固定开场。

**语气与用词**：只说"我会改成什么"，不说"原来哪里不好"；不说乱、脏、垃圾。不说免费或付费，只说次数：实际用了生成就写明"用了 N 次生成"。回复中不出现内部术语：

| 内部 | 对用户说 |
|---|---|
| 身份层、状态层、拍法层 | 不说层名 |
| 让位 | 留着，放到边上 |
| 内部锚点 | 已认可成图（仅说明实际参考职责） |
| 额度 | N 次生成 |
| 本地轻修 | 只调色 |
| 生成式编辑 | 按所选模式说“修好”或“按你的照片重拍”（用 1 次） |
| `画面来源` 值 | 你的照片（修好） / 按你的照片重拍 / 我设计的画面 |

## 路由

| 用户回复 | 执行 | 授权 | 必说的实话 |
|---|---|---|---|
| 明确要单图 | 按创作或修改意图选执行路径，不一律修原片 | 按“授权与张数”执行，evidence 指向实际消息 | 报路径、保留范围与次数 |
| 开始做（一套） | 按已批脚本逐项执行 | 按已批总张数授权或使用现有有效授权 | 报本轮总生成次数 |
| 已授权范围内继续 | 按剩余计划逐项 prepare | 沿用有效授权 | 报本轮生成次数 |
| 点头修正某张 | 对选定成图局部修改，以该版为父版 `generative_edit`、`input_policy="legacy_edit"`；用户要求整幅重新策划才重列借用范围并用 `explicit_scope` | 先核现有授权是否覆盖；不足才补授权；`extend_retry_budget`只扩重试额 | 用 1 次，报累计 |
| 开始做（各自一张） | `independent_items`，每项按创作或修改意图选路径 | 按“授权与张数”核对已有范围 | 将用 N 次生成 |
| 已说明的模糊图文字重建 / 补出的设计节点 | `create_work` → `generate`，不传父版和参考 | 按本轮已授权的项数；不额外加次数 | 不带原图，是设计画面，菜的具体外观可能变 |
| 只补充要求 | 更新适用要求；明确同时要求执行且有授权时推进 | 不由补充本身增加授权 | — |
| 只调色 | `create_work`＋`import_image` → `local_edit` | 无（0 次） | 不能挪东西、不能改光；首答承诺的收拾或放边上在此路线不兑现，要说并提供重拍 |
| 去背景 / 白底 / 去掉某物 | 原生语义编辑；透明底用 `transparent_background` | `authorize(1)`：首句已明确则直接用，否则等开始 | 用 1 次；主体可能被重画 |
| 补全成一个故事 | 摄影脚本 | 见“授权与张数” | 写明总张数及还需生成次数 |
| 给几个方向 | 2–3 个具体方向，只读，按[interaction.md](interaction.md)探索规则 | 无 | 不出图 |
| 怎么拍 / 拍得怎样 | 点评或实拍指导，只读 | 无 | 不出图 |
| 认错菜、关系答复 | 回到分析，重出首答或短确认 | 无 | — |
| 加字、logo 或文字版式 | 告知“加字暂不支持”，可先给文案；按[state.md](state.md)“作品记录”保存需求，并在当条回复中用自然话说明已记下的内容；尚未落盘时如实说明实际记录位置与缺口 | 不授权任何带字图生成 | 所有路径均不生成、不计划生成新增文字或 logo 的图片 |
| 原生图像工具不可用 | 说明缺口，不用旧 CLI 或其他渠道补位 | 无 | — |

"回第一版继续""看第一版"沿用[interaction.md](interaction.md)的选版规则。

## 需求记录

- **单图**的保住、放掉、改动写进 `prepare.changes`，来源如实：用户说的 `user_explicit`；用户没说、但照片里真实可见的身份元素用 `user_implied_edit_preservation`——只用于照片里真实可见的默认保留项，不用于推测的偏好或我们新增的设计；我们的改动 `ai_design`。**不要用 `default` 记身份保留**：`default` 低于 `ai_design`，会被风格展开覆盖。
- 设计展开不得生成与身份保留冲突的条件。引擎只裁决同键冲突，不同键的语义冲突须在准备时按[styling.md](styling.md)的统一优先级自查。
- 作品、条件档位、脚本、已用命题、本轮决定和计数统一按[state.md](state.md)“作品记录”保存；普通摄影要求与来源按下列规则落实。
- **一套图**：`prepare.changes` 只作用于单个 Request，后续项不继承。用户对整套说"开始做"时，用 `add_requirements` 将卡片中的 `组级故事设计` 记为 group 作用域：整组讲什么、场景怎样衔接、人物安排与共同视觉方向。它描述整组关系，不等于每张都包含全部场景。共同身份和真正适用于全部镜头的条件另行记录；只适用于部分镜头的场景/服装/关键物件连续条件用 group scope 的 `item_ids` 限定，不能锁到转场项。`message_id` 用实际消息 ID，用户明确条件记 `user_explicit`，自主设计记 `ai_design`；不因用户说“开始”就把 AI 选的厨房或服装记成用户指定。
- **逐图传递**：每次 `prepare.changes` 记录 `本张叙事任务`：本张在整组中的作用、场景及与前后镜头的关系、动作/食物阶段、景别机位；本张具体设计按 `ai_design`，用户点名条件保留其来源。同时在 `prompt` 中组织成可执行画面，与适用的组级条件及 Reference borrow/exclude 一致。`prompt` 开头先写本张的机位与景别，只写本张这一种，不附其他镜头的机位规则；连续项写在其后，不得以连续项改写本张取景。特写写明主体（如筷尖上的那块鱼肉）以及哪些东西允许出画。“菜完整”是场景状态，前面镜头交代过后，特写不要求整道菜入画，也不写“不裁掉菜的关键部位”这类会把画面撑回中景的限制。用实际 preview 核对这些内容和实际附图，不以卡片或另存计划代替请求。阶段状态与局部拍法逐项写，用户明确说"以后都"才用 project 作用域。
- **`画面来源`**：专用键只由本 Skill 以 `ai_design` 写入；值 `用户照片`（展示“你的照片（修好）”）、`照片重拍`（展示“按你的照片重拍”）、`设计画面`（展示“我设计的画面”）。照片为父版的大幅重构用 `照片重拍`；文字新生成和补节点用 `设计画面`，文字降级还须说明“按菜名重建，未使用原图”。不改写旧 Version 的值。每个 Work/组项首次 prepare 写入；以后检查缺失或与当前路径不符才在新 Request 补写/更新，同轮只写一个值，不用其他来源。换 Work 不继承此键；交付读目标 Version 有效要求，不能仅凭操作类型、父版或参考推断标签。旧值 `用户照片`/`设计画面` 继续按上述含义展示。
- **切换模式**：记录用户选择，重列本轮保留项。原有 `user_explicit` 锁定未被撤销就继续保留；从修图转创作时，若父版留有器皿等隐含锁定，用同键 `user_explicit` 记录用户选择允许更换的范围（例如“器皿可按故事更换”），具体新器皿设计另用 `ai_design`，不把 AI 选的器物冒记为用户指定。不只新增一个模式键便假定旧锁定消失。
- **切回修图**：先确定用户要修的底图，原照片与创作版指代不明时先消歧；不自动取最新生成版。对原先因创作模式而放开的同键，以本次切回修图的 `user_explicit` 覆盖为“依指定修图底图保留，撤销更换许可”；具体 AI 设计仍按 `ai_design` 同键更新（如 `器皿设计=依指定修图底图`），以较新 revision 替换旧 AI 换盘方案；不要把具体 AI 设计的撤销写成 `user_explicit`，否则再次转创作时 AI 方案无法覆盖。后续每次切换都更新“器皿”许可键与“器皿设计”方案键；前者记录用户允许的范围，后者只记录 AI 方案，不能只改模式名称或添加低来源保留项。用户单独点名的锁定或更换要求仍需按实际指令处理，有冲突先说明；整组切换按相应作用域更新，不能只改一张代表图。来源标签按实际底图和画面依据更新，对既有创作版的局部修正不改称“你的照片（修好）”。

## 创作：策划与方案

### 先定拍法、事件与镜头

拍法有四种：过程叙事、生活一刻、成品特写、细节拆解（含食材）。过程叙事仅包子验证过一次，后三种【待验证】，作为候选做法而非效果承诺；按本轮情境选择，不固定从原料到收尾的生命周期。

场景依据依次为用户明说、照片事实（外卖或堂食、份量、餐具、环境）、时刻、地域吃法、菜；菜名只决定器物和动作，不凭菜名编整套地方背景。没依据时选证据最足、假设最少的时刻，自编一句事件：谁、何时、为何吃这顿、正在做什么；首答用一句理由交代选择，理由要落到可见依据或这道菜的常见吃法（如“一桌六个菜、三副碗筷的量，像家里周末聚餐”），只说“这是设计”不算理由；不列场景菜单、不为此追问。创作时照片只作菜和这顿饭的依据：看得到的餐具、饮品可沿用作线索，桌面与环境按事件重新设计，不把整套锁在照片那张桌上。用户讲过自家细节则按其反推；新增角色与经历是设计，不冒称照片事实。套图场景随这顿饭的前后推进而变化，沿同一生活线；食材溯源可选，非每道菜必需。

从一句事件推导动作链，每张一个主动作及其留下的痕迹（如水汽、空位、断面、食物变少），角色必须具体，不能只写“有人”或以不露脸代替角色。避免摆满、齐刷刷伸手、暖黄滤镜代替事件。人数、餐具与取景用[styling.md](styling.md)校验表检查，人物、路线与明暗也在该文件统一判断。这种烟火表达方法【待验证】。

逐镜头先定故事作用与可见画面，再决定景别、机位、光位与道具；原图数量、摆位不代替设计。一套里相邻两张的景别与机位至少一项明显不同；三张及以上至少用到两种机位高度（顶拍、斜俯、平视或食客自己的视线），只改角度几度、手上动作不同不算换视角。用户版每张在“画面一句”写明从哪里拍。同场景保留需要连续的条件，转场只延续仍适用项，不强制每镜头换景或同台面。

### 方案表达

- 面向用户直接给本轮方案，套图回复依次为：① 一句事件及本轮场景、明暗的画面理由；② 完整摄影脚本用户版，逐镜头用“编号｜故事作用｜画面一句｜景别｜画幅｜光与明暗｜主要道具｜连续项（跨镜头保持什么）”八字段填全；③ 下方“方案收尾”。景别与机位分开，画幅含方向与比例；共享条件放在脚本前并标出适用镜头，不用“沿用”代替缺失内容。
- 执行版与用户版逐项对应，补具体机位、光向、身份保留、食物阶段、执行路径、参考职责；把组级设计与本张任务实际写入 `prepare.changes/prompt`，不只停留在卡片标题。
- 单图回复依次为：① 画面（含事件与构图）；② 明暗（含本轮理由）；③ 主要道具；最后接下方“方案收尾”。三项不限定物理行数或具体措辞。
- 再拍一套回复分三段：① 与上一套的关系；② 新脚本或仅需重拍的几张；③ 下方“方案收尾”。
- 修改不出脚本，只说改什么、保留什么；点名一张只处理该张。实拍指导复用相应摄影脚本格式，保持建议模式。
- 已认可单图转套图：保留该图作第一张，补完整脚本，区分总张数与还需生成张数；不默认重新生成第一张。

创作与重拍方案的最后一段：

| 方案状态 | 方案收尾 |
|---|---|
| 用户尚未批过的新方案：首次套图、新脚本、新重拍方案、单图方案或换菜后新方案 | 本轮 N 张，将用 M 次生成，可以吗？ |
| 用户已批的同一方案：复用已批脚本、已批方案内分批 | 本轮 N 张，将用 M 次生成。 |

N 是本轮计划生成张数，M 是相应生成次数；单图未指定张数时 N 为 1。保留已有图时，总张数与本轮新增数分开说明。方案批准以用户对已展示的本次具体安排的同意为据；额度授权（次数、渠道）与剩余额度只用于核算能否执行，不构成方案批准，不能据此选择上表“用户已批”一行。

### 按镜头选执行路径

1. 原图编辑：以对应照片 Version 为父版。普通修图、选定成图的局部改动用 `generative_edit`、`input_policy="legacy_edit"`；只改用户明说范围，保留边界见[styling.md](styling.md)。
2. 整幅重策划且选择原图作父版：用 `generative_edit`、`input_policy="explicit_scope"`，先 `add_reference` 建显式 `base_image`，`borrow` 写本阶段适用的菜身份与锁定项，`exclude` 写不继承的原构图、机位和已放开物件。主图 asset 匹配父版，强度 `required`，`prepare.references` 显式提交 ID。排除表示按新设计处理，不是禁止该类物件；锁定项不得同时排除。
3. 文字新生成或设计补节点：`generate`，不传父版、参考或 `explicit_scope`，文字写明菜品身份、适用组级条件和独立画面；若选择借参考则按“参考图”定职责并走可接收图片的编辑路径。

初次创作不强制以原图为父版。路径只决定提交方法，不能保证身份、构图或属性分离成功；按原图重拍与新策划均如实标来源，接口细节见[codex.md](../hosts/codex.md)。保留主体尺寸目标，具体尺度服务构图；“身份签名加相对尺寸”尚未验证达成，不当作已证实修法。

### 授权与张数

方案批准与确认收尾统一见“方案表达”。获批后可直接完成整套，也可在同一总数内分批生成、每批自查后继续，不强制样张、不逐张重批。只说方向或单独补要求不授权生成。计划超出已批范围时回到方案表达，并按入口原则附推荐。次数与停止条件见“出图后”。

## 出图后

- 原图与新图依次展示并对应标签；宿主不支持并排时按顺序发，不另做拼图，除非用户要。
- 按当前模式检查：创作逐图与整组均分别核菜的身份签名、用户锁定项、新构图与机位、故事作用及阶段食物状态，再核整组共同条件。对照 `本张叙事任务` 看动作、空间或关系是否实际可见，不能只凭标题解释“有故事”；已出图只验证其覆盖的方向，未呈现的转场或连续性保持未验证。用户提供已认可作品时，按其点名的审美因素对照，不把旧菜、固定厨房或镜头数量变成新任务模板。身份更像不能抵消叙事未达成，技术检查也不能代替用户审美认可。修图按身份表逐项核对；不要拿修图的器皿默认锁定去否决创作模式主动换盘。
- 逐项核对默认保住的项和用户新锁定的项，一行一项："碗：颜色对，纹理略细；青菜：在；铜锣烧：在，但变成三块。要修哪个？"肉块形状、青菜样子、釉面纹理、筷子材质易漂，优先核对。
- 对承诺重做拍法的请求，检查机位与取景是否确有变化，台面/背景是否按方案重设计，光位变化是否有受光与投影依据；只提亮不算完成。没有足够视觉依据就标不确定，不把工具成功或新增道具当作机位改变的证据。
- 每次修正先核同一问题的累计失败次数：连续两次未修好时，结束本轮尝试，交付当前可用版并说明具体限制；替代办法（换路径重拍、改方案或实拍建议）留作后续选择，不接着安排修改、报下次执行次数或索取续修素材。停止前的催修不算停后坚持。交付收束后，用户再次坚持才改用另一种办法，并先说明路径变化；执行前按“授权与张数”核对方案与次数，不重用失败办法。尚未触发停止时，先按 P-CHECK 核对请求与输入有无漏写、误锁，只说这次尝试没做到，不由单例断言工具极限。问题计数不因新建版本、换标签而清零。
- 生图前核对本次计划与总授权、已用和未知占用。剩余次数不够整套时，先推荐减张，或只在剩余额度内分批；分批不重置、不增加总额度，不暗示分完就能超额做完。新增额度须有实际授权，失败、重做与未知结果调用照实计账。
- 对用户用“将用 N 次生成／用了 N 次生成”表达计划与实际，不说免费或付费；没有执行不得写成已用。本地调色裁切为 0 次生成。额度授权不覆盖越界操作，也不取消上述停止条件。
- 用户没要透明底时，检查新图有无透明像素；有明显透明区域（如边角、背景被挖空）要告诉用户，并提供修正（用 1 次）或改用只调色原图。带 alpha 通道的原图（即使全不透明）更容易出现这种情况。

## 参考图

按职责区分两类，角色与提问遵循入口规则。

### 外部风格参考

- 用户发自己的照片、只要求套用参考的感觉时（属修图）：只借光、色、质感，先翻译成具体文字描述，再在用户原图上编辑；写明保留菜、器皿、场景、构图与核心元素，不顺带换桌面、摆位或道具；确实非换场景不可时，才问保原照片还是接受重拍，并推荐较符合目标的做法。
- 创作单图或套图带参考时：参考只转成光、色、质感的文字，用到按事件重新设计的场景里，不在原图上编辑、不保留原图构图；场景按“创作：策划与方案”。
- 用户明确要求复刻或同构图时，按点名范围尽量接近并说明不能保证一模一样；未点名项仍用默认借法，不以通用禁止复刻代替用户选择。菜的身份与其他明确条件仍有效。
- 默认只作用于当前这一张，用户明说整套才扩展；套图中途加入参考而范围不明时，只问当前一张还是后续整套，推荐先用于当前张。明确范围就直接照做；已认可或已完成项不自动重做。
- 参考中的人脸、白底默认不带入，并向用户说明；不新增文字、商标或 logo。多张参考存在明暗等实质矛盾时不平均，问以哪张为主或分两版，附推荐。
- 只点名某博主但无图：请发一两张参考以便具体判断，同时把补图作为可选项，说明不发也能按本轮默认方向继续，并简述该方向；不因缺参考挂起当前任务，不冒称知道其稳定风格，不联网查图。
- 语义借鉴与保留效果【待验证】：不承诺属性完全分离或完全不受参考影响，出图后逐项检查借到了什么、串入了什么。

### 同套连续性参考

用于单张重拍（整套首次生成时同机位高度镜头从第一张出发，见“创作”执行顺序第 3 条）：从本套已认可成图参照一次，借菜的身份、器物、光向与色调保持整套一致；不得将参照生成的下一版继续串作下次参考，避免成图到成图长链。原认可参考不可用时说明缺口，不用未认可版替代。其他职责明确的人物、器物、空间参考，可按镜头需要使用；连续性效果【待验证】。

### 记录与提交

参考素材用 `import_asset` 登记，不创建作品版；`add_reference(asset_id, roles, scope)` 逐角色记录 `role/borrow/exclude/strength/source`，并在 `prepare.references` 显式提交实际需要的 Reference ID。外部参考 scope 默认限当前项，用户点名后续项用 `item_ids` 限定，不扩成整项目。保留与排除不得语义冲突；用户器皿与借来感觉冲突时默认保用户器皿，仅调整冲突属性。

借来的感觉写在 Reference roles；展开为需求时用 `ai_design`，不用较高优先级的 `user_reference` 覆盖原图身份保留。编辑有一个明确主底图，总输入最多三张，不为凑参考数量丢掉必要素材；新生成不附图，改用适用的文字描述（同场景且机位高度与第一张相同的镜头改走编辑路径，见执行顺序第 3 条）。单张重拍的系列绑定接口见[state.md](state.md)；不因接口支持锚点就将其扩为强制样张或连续生成链。

## 交付边界

- 本地调色裁切保留原图已有的 ICC 配置，不转换到 sRGB，也不补配置文件；只支持单帧 8-bit RGB/RGBA。RAW、高位深和印刷交付不支持，用户提到时先说明；需要 sRGB 转换属于另外的功能，当前没有。
- 平台常用比例与一次裁出多个比例见[interaction.md](interaction.md)的"比例预设"。
- 不核查照片是否用户本人拍摄；九宫格或拼图单文件多菜按多图分组尝试，效果未验证；用户中途不回复时不追发。
